# Super Mario 64 for PSP

🌐 **English** · [Español](README.es.md) · [Français](README.fr.md) · [Deutsch](README.de.md) · [日本語](README.ja.md)

A native port of **Super Mario 64** for the **Sony PSP**, available for the **US, Japanese (JP), European (EU) and Shindou (SH)** versions, based on the
[sm64-port](https://github.com/sm64-port/sm64-port) / [n64decomp/sm64](https://github.com/n64decomp/sm64) decompilation
and the PSP port by [z2442](https://github.com/z2442/sm64-port).

**What this version adds**

- Choice of **30 or 60 FPS**, with frame-pacing options.
- Audio is generated by the PSP's **Media Engine** (the second CPU), which frees the main CPU for the game.
- An **in-game Options menu** (open it from the pause screen) with three pages: **Graphics**, **Audio** (music volume, effects volume and sound mode) and **Controls** (remap every button).
- All settings live in **one readable text file**, `sm64config.txt`, that you can also edit by hand.
- Progress is saved on the Memory Stick like a normal PSP game.
- **Four versions from the same code**: US, JP, EU (English, French and German, with the PAL layout adapted to the PSP's 16:9 screen) and Shindou (experimental). See [Supported versions](#supported-versions).

> **This repository does not contain the game's data.** You need your **own copy of the Super Mario 64 ROM** of the version you want,
> which the build process turns into the PSP version. No ROM is included and none will be provided.
> This is a fan project and is not affiliated with Nintendo.

## 1. What you need

| Thing | Details |
|---|---|
| **A PC** | Windows 10 or 11, 64-bit, about **10 GB of free disk space** and an internet connection (only for the first build). |
| **A Super Mario 64 ROM** | The version you want to build, in **`.z64`** format (8 MB, "big-endian"). The exact file name and SHA-1 for each version are in the table below. |
| **Docker Desktop** | Free for personal use. It provides the whole PSP compiler for you, so you do **not** have to install any developer tools. |
| **A PSP with custom firmware** | For example ARK-4 or PRO CFW, and a Memory Stick. *Or* the [PPSSPP](https://www.ppsspp.org/) emulator. |

The only thing you install on the PC is Docker Desktop. Everything else (compiler, Python, libraries) lives inside a Docker container
that the build script creates for you.

**PSP-1000 (24 MB of RAM):** the game is meant to fit in a PSP-1000's memory, and it boots and runs in PPSSPP set to a 24 MB model with roughly 2 MB of heap to spare. It has **not been tested on a real PSP-1000** yet, so treat it as experimental there. TV output is not available on a PSP-1000.

### Supported versions

| Version | File name(s) you must provide | SHA-1 of the ROM | Status |
|---|---|---|---|
| **US** (USA) | `baserom.us.z64` | `9bef1128717f958171a4afac3ed78ee2bb4e86ce` | Main version, the most tested. |
| **JP** (Japan) | `baserom.jp.z64` | `8a20a5c83d6ceb0f0506cfc9fa20d8f438cafe51` | Builds; less tested. |
| **EU** (Europe) | `baserom.eu.z64` | `4ac5721683d0e0b6bbb561b58a71740845dceea9` | English, French and German. Tested on PSP and PPSSPP. |
| **SH** (Shindou, Japan 1997) | `baserom.sh.z64` **and** `baserom.jp.z64` | `3f319ae697533a255a1003d09202379d78d5a2e0` (SH) | **Experimental.** Graphics and game come from the SH ROM, but the sound still comes from the JP ROM, so the audio is not the real Shindou one yet. |

Each build is its own game: the version you build is the version you get. Rename your ROM exactly as shown (all lowercase).

**Known limitations**

- The Shindou version needs **both** ROMs (SH and JP) and uses the Japanese sound data and audio engine (the original Shindou sound engine is not ported yet). Rumble is not available (the PSP has no rumble motor).
- All versions share the same save folder and file name (`PSP\SAVEDATA\SM64PORT\sm64_save_file.bin`). Saves of different versions are not guaranteed to be compatible, so **back that file up before switching to another version**.

## 2. Building it on Windows, step by step

### Step 1 — Check your ROM

(The example uses the US ROM; for another version compare with its SHA-1 from the [table](#supported-versions).)

1. Make sure Windows shows **file extensions**: in File Explorer open **View → Show → File name extensions**.
   (If extensions are hidden, a file you rename to `baserom.us.z64` may secretly become `baserom.us.z64.z64`, and the build will not find it.)
2. Right-click the Start button → **Terminal** (or **Windows PowerShell**) and run, changing the path to where your ROM is:

   ```powershell
   Get-FileHash -Algorithm SHA1 "C:\path\to\your\rom.z64"
   ```

3. The result must be exactly `9BEF1128717F958171A4AFAC3ED78EE2BB4E86CE` (US).
   If it is different, your ROM is not that version, or it is in another format (`.v64` / `.n64`). The build needs the `.z64` format.

### Step 2 — Install Docker Desktop

1. Download it from <https://www.docker.com/products/docker-desktop/> and run the installer.
   Keep the option **"Use WSL 2 instead of Hyper-V"** ticked (the default).
2. Restart the PC if the installer asks you to.
3. Open **Docker Desktop** from the Start menu and accept the terms. Wait until the bottom-left corner shows
   **"Engine running"** (green). **Docker Desktop must be open every time you build.**
4. To confirm it works, open a PowerShell window and run:

   ```powershell
   docker --version
   ```

   You should see something like `Docker version 27.x.x`.

> If Docker complains about **virtualization**, it has to be switched on in your PC's BIOS/UEFI
> (look for "Intel VT-x", "SVM Mode" or "Virtualization Technology" and enable it). See [Troubleshooting](#5-troubleshooting).

### Step 3 — Download the project

The easiest way, with no extra programs:

1. On this repository's page click the green **Code** button → **Download ZIP**.
2. Extract the ZIP into a **short folder without spaces or accents**, for example `C:\sm64-psp`.
   Avoid very long paths and avoid folders synced by OneDrive.

*(If you already use Git, `git clone https://github.com/Edwintendo/sm64-port-psp.git` works too.)*

### Step 4 — Put the ROM in the project folder

1. Copy your ROM into the project folder, **next to the file called `Makefile`**.
2. Rename it to exactly **`baserom.<version>.z64`** (all lowercase), where `<version>` is `us`, `jp`, `eu` or `sh`: for example `baserom.us.z64`.
   The Shindou version needs two files: `baserom.sh.z64` and `baserom.jp.z64`.

The folder should now contain, among others: `Makefile`, `build_psp.ps1`, `Dockerfile.psp`, `src`, and your ROM (`baserom.us.z64`, for example).

### Step 5 — Run the build script

1. Open the project folder in File Explorer, click an empty area of the address bar, type `powershell` and press **Enter**.
   (That opens PowerShell already inside the folder. On Windows 11 you can also right-click an empty area → **Open in Terminal**.)
2. Run:

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\build_psp.ps1
   ```

   That builds the **US** version. For another version add `-Version`:

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\build_psp.ps1 -Version eu
   ```

   (`us`, `jp`, `eu` or `sh`.) The `-ExecutionPolicy Bypass` part lets Windows run the script just this once, without changing any setting.)

3. Wait. The **first time** it does three things, and it is slow, so be patient:
   1. Downloads the PSP compiler and builds a small Docker image called `sm64psp` (a few minutes, needs internet).
   2. Extracts the graphics and sounds from your ROM.
   3. Compiles the game (this part takes the longest; the screen fills with text, which is normal).
4. When it finishes you will see:

   ```
   Listo: build\us_psp\mario64\  (copia EBOOT.PBP y SM64.PRX juntos a la misma carpeta de la PSP)
   ```

   (The text is in Spanish; the folder name changes with the version: `build\eu_psp\mario64\`, `build\jp_psp\mario64\`, `build\sh_psp\mario64\`.)

   Next builds are much faster: only what you changed is recompiled.

**Optional script switches**

| Command | What it does |
|---|---|
| `.\build_psp.ps1 -Version eu` | Chooses the version: `us` (default), `jp`, `eu` or `sh`. |
| `.\build_psp.ps1 -Clean` | Deletes the previous build of that version first. Use it if something is broken or stuck. |
| `.\build_psp.ps1 -Opt O2` | Builds with `-O2` instead of `-O3` (separate folder: `build_O2\`). |
| `.\build_psp.ps1 -Rebuild` | Rebuilds the Docker image (only needed if `Dockerfile.psp` changes). |

(Remember to put `powershell -ExecutionPolicy Bypass -File` in front if you use them, e.g.
`powershell -ExecutionPolicy Bypass -File .\build_psp.ps1 -Version eu -Clean`.)

### Step 6 — Find the result

The game is the pair of files **`EBOOT.PBP`** and **`SM64.PRX`** inside **`build\<version>_psp\mario64\`** (for example `build\us_psp\mario64\`). Always keep them together in the same folder: `EBOOT.PBP` is a tiny loader and `SM64.PRX` is the game itself (this makes it start much faster on a real PSP).

## 3. Putting it on your PSP (or running it in PPSSPP)

### On a real PSP

1. Connect the PSP to the PC with a USB cable and enable **USB Connection** from the XMB, *or* take the Memory Stick out and put it in a card reader.
2. On the Memory Stick, open the **`PSP`** folder, then **`GAME`**.
3. Create a new folder called **`SM64`** (use another name, e.g. `SM64_EU`, if you install several versions) and copy **both** `EBOOT.PBP` and `SM64.PRX` into it, so the paths are:

   ```
   PSP\GAME\SM64\EBOOT.PBP
   PSP\GAME\SM64\SM64.PRX
   ```

4. Disconnect the PSP. On the XMB go to **Game → Memory Stick** and you will find **Super Mario 64**.

> Your PSP needs **custom firmware** (ARK-4, PRO, ME, …) to run homebrew. This port was developed and tested on a PSP with **ARK-4 at 333 MHz**.
> On a **PSP Go**, copy the folder to the internal storage's `PSP\GAME` folder instead.

### Without a PC: install from a release

If a release is published for your version (GitHub → *Releases*), you do not need to build anything or install Docker. The release contains no data from the game: it prepares itself from **your own ROM** the first time you start it.

1. Download the zip of your version (`SM64-PSP-us.zip`, `-jp`, `-eu` or `-sh`), extract it and copy the **`PSP`** folder to the root of your Memory Stick (merge folders if asked).
2. Put your own ROM in `PSP\GAME\SM64_<VERSION>\data\` (any file name; `.z64`, `.v64` or `.n64`). The Shindou version needs both the SH and the JP ROM.
3. Start **Super Mario 64** from the XMB. The first time it checks your ROM and builds the game (a progress bar is shown and it can take a while), then it starts. The next times it starts directly; the ROM, `SM64.template.prx` and `manifest.bin` are no longer needed and can be deleted.

The installer shows its messages in the language of your PSP (English, French, German, Spanish, Italian or Japanese). If it says the ROM is missing, check that it is the original 8 MB ROM of that version (SHA-1 in the [table above](#supported-versions)). The installer has been tested on a real PSP-3000; reports from other models (especially the PSP-1000) are welcome.

### Optional: TV output (experimental)

The game can send its picture to a TV through the PSP's video cable. It only works on a **PSP-2000 / 3000** (not on a PSP-1000; the PSP Go has not been considered) and uses a small helper module that is already **inside `SM64.PRX`** (the game writes it to the save folder and loads it when needed), so there is nothing extra to copy. Open **Options → Graphics → TV Settings** (a sub-page that only opens while a video cable is connected; without the cable the row is grey, shows *No cable* and, if you unplug the cable while inside, the menu takes you back to Graphics) and set **TV Output** to **240p**, **480i** or **480p** (**480p** needs a *component* cable; **240p** and **480i** also work with a composite/AV cable, and **480i** is the one to use with an AV-only TV). The change is applied **right away**, without restarting the game (it waits about half a second after you stop changing it). The game reads the real cable state with a second small read-only helper module (also inside `SM64.PRX`), and **the TV is only used while a video cable is plugged in**: with TV Output selected, the bottom of the menu shows **No cable / AV cable / Component cable** (plus the measured refresh rate of the TV mode). If the cable is not plugged in the picture stays on the PSP screen (also at start-up; your TV Output setting is kept), and when you plug the cable in the TV turns on **by itself** in the chosen mode; if you unplug it, the picture goes back to the PSP screen. **The cable is mandatory:** without a detected cable the row cannot be moved to a TV mode (it plays the "can't move" buzz and is greyed out while it is Off); you can always go back to Off. If that helper cannot load on your firmware, the game cannot know about the cable and falls back to the old behaviour (assumes a component cable; **L** reconnects by hand). The row stays **grey** (it shows the reason, e.g. "PSP-1000" or "Safe mode", and plays the "can't move" buzz if you try to change it) if the console is a PSP-1000, or if the helper could not be loaded.

Related options and tools (all on the same Graphics page, except TV Output / TV Aspect / TV Width / TV Height / TV Vertical Shift / Reset TV Settings, which live in the **TV Settings** sub-page; *Reset to Defaults* on the Graphics page does not touch the TV settings):

- **TV Aspect**: which view the game draws. *4:3* is the original N64 view (a narrower picture, 362×272 internally, with the original 3D projection) and *16:9* is the widescreen view (480×272). In both cases the picture fills the whole video frame and the **TV decides how it is shown, so set your TV to its matching picture mode: 4:3 for *4:3*, 16:9 / wide / full for *16:9*.** The change is applied right away. In *4:3* the whole 3D scene (the world, the file select and star select menus, Mario's head) uses the original 4:3 projection, so everything keeps the proportions of the N64 instead of looking squeezed.
- **With TV Output *Off*** the rest of the TV Settings page (TV Aspect, TV Width, TV Height, TV Vertical Shift and Reset TV Settings) is greyed out and does nothing, and the guide frame is not drawn: there is no TV picture to adjust. In every options page the cursor skips greyed-out rows (except "TV Settings" in Graphics, which can still be selected so "No cable" is shown at the bottom; pressing it then plays the buzz); if everything that is left in that direction is grey (as here) it does not move and Lakitu's "camera can't move" buzz plays.
- **TV Width** and **TV Height**: *60%* to *100%* in steps of *1%* (default *100%*), set separately because TVs rarely cut the same amount horizontally and vertically, and because with different values you can also correct a picture that looks slightly squashed or stretched (lower *TV Width* a few points against *TV Height* if the picture looks too tall-and-thin or too wide, and the other way round). Many TVs cut off the edges of the picture (overscan), so part of the game (the HUD, for example) can end up off screen. While the **TV Settings** page is open a white frame is drawn on the very edge of the real picture (the full 16:9 width in the *16:9* aspect): lower *TV Width* until the left and right lines are fully visible and *TV Height* until the top and bottom ones are (holding the D-pad repeats). The rest of the video frame is left black. It is applied right away, without re-initialising the TV output, and works in every TV mode and in both aspects. A `tv_area` line from an older settings file is read as both values.
- **TV Vertical Shift**: *Up 60* to *Down 60* (*0* by default), in lines of the 480-line video signal. It moves the picture up or down inside the video frame, for TVs that leave an empty band at the top or the bottom (the guide frame moves with the picture). The picture cannot leave the video frame, so it needs room: with *TV Height* at *100%* there is nothing to move; lower *TV Height* a little first.
- **480p test**: after you choose 480p the game waits **10 seconds** for you to press **A** ("A: keep 480p" shows at the bottom of the menu). Only 480p asks, because many TVs and AV cables cannot show it; 240p and 480i switch right away with no question. If you do not confirm (for example because your TV cannot show 480p, or you cannot see the picture), it goes back by itself to the previous mode. **B** cancels at once. While the test runs the rest of the menu does nothing.
- **Reconnect the cable**: if you unplug the video cable and plug it in again, select **TV Output** and press **L** to send the picture to the TV again.

How it works, and its limits:

- **Sound with the video cable**: the AV cable uses the same jack as headphones, so the PSP sends the sound through it and mutes its own speakers. With a video cable connected and *TV Output* set to *Off*, the game asks the system (`sceAudioRoutingSetMode`) to play the sound through the PSP speakers again; as soon as TV Output is turned on, the cable is removed or the game exits, the normal automatic mode is restored. With headphones (no video cable detected) nothing is changed. I could not test it on real hardware: if the speakers stay silent, please report it.
- **HOME button with TV output on**: while a TV mode is active the HOME button does nothing. The firmware's exit dialog is drawn garbled on the TV and leaving the game with the TV signal still on makes the PSP fail, so HOME is disabled on purpose; pressing it plays Lakitu's "camera can't move" buzz and shows *Turn TV Output Off to exit* at the bottom of the screen for a few seconds. To leave the game, first set *TV Output* to *Off* in the options menu; with the PSP screen HOME is the normal firmware one again. This relies on `sceImposeSetHomePopup`; I could not test it on real hardware with ARK, so if the old dialog still appears with the TV on, please report it.
- The game is still drawn at 480×272 and the result is scaled to the TV with a bilinear filter, (the widescreen view in *16:9*, or the 4:3 view, 362×272, in *4:3*). It is not a native 480p render. **240p** uses the same video signal as 480i (the one that has been seen working on a real TV), but both fields carry the same 240 lines, so you get a stable 240-line picture without interlacing (asking the DVE for a raw 320×240 mode did not engage the TV on a real PSP-3000: the picture stayed on the PSP screen). **480i** is 720×480 interlaced (two fields of 240 lines, as in the OoT port) and is the TV-friendly high resolution; unlike the old single-buffer path it is no longer forced down to 30 fps; the game does not know which field your TV shows first, so if the picture looks very slightly shifted up/down compared with 480p that is why.
- To be able to switch without restarting, on a PSP-2000 / 3000 the game loads the helper and switches the video memory to 4 MB **every time it starts** (as the OoT port does), even if TV Output is *Off*. With TV Output *Off* the game is drawn the same way as before. In **480i** and **480p** there is room for only one output buffer, so there can be a tear line when the picture changes. 240p uses three buffers and does not have this problem.
- **This is experimental.** It has been tested on a real PSP-3000 with a component cable; **480p has not been tested** (the TV used does not support it) and neither has composite/AV output. If you try it, please report what you see.
- Safety net: if TV was turned on and the game did not get to about 5 seconds of play with it, the next launch goes back to the PSP's screen and sets TV Output to *Off* by itself.

### In PPSSPP (PC / Android)

Open PPSSPP and use **Load…** to pick `EBOOT.PBP` (keep `SM64.PRX` next to it), or drag the file onto the PPSSPP window.

## 4. Playing: controls, options menu and saves

### Default controls

| PSP | Does |
|---|---|
| **Analog stick** | Move Mario |
| **✕ Cross** | A (jump) |
| **□ Square** | B (punch / dive) |
| **○ Circle** or **L** | Z (crouch / ground pound) |
| **R** | R (camera mode) |
| **△ Triangle** | N64 "L" button (the game doesn't use it) |
| **D-pad** | C buttons (camera; Up = first-person view) |
| **Start** | Pause |

You can change all of these in the Options menu.

### The Options menu

1. Press **Start** to pause the game.
2. Press **R** (the pause screen shows "**R Options**" at the bottom right).

| Buttons | Action |
|---|---|
| D-pad / stick **up–down** | Move between options |
| D-pad **left–right** or **✕** | Change the value / enter a page |
| **□** or **○** | Go back |
| **Start** or **R** | Close the menu (and save everything) |

**Pages**

- **Graphics** — FPS Limit (30 / 60), Frame Pacing (*Keep FPS* / *Keep Speed*), Object Distance and Far Distance (100 %–300 %),
  Object Culling (*Original* / *Vertical*), FPS Counter, Show Sound CPU, **TV Settings** (sub-page, needs a video cable: see section 3: TV Output (*Off* / *240p* / *480i* / *480p*; applied right away; only 480p asks you to confirm), TV Aspect (*4:3* / *16:9*), TV Width and TV Height (*60%* to *100%*), TV Vertical Shift, Reset TV Settings), Reset to Defaults.
- **Audio** — Music Volume and Effects Volume, from 0 to 100 (100 is the game's original loudness), and Sound Mode: Stereo, Mono or Headset. Sound Mode is the same setting as the one in the file-select screen (it is saved in the save file, so changing it in either place changes both).
- **Controls** — choose a button and press **✕**; the screen says "Press a button" — press the PSP button you want (it waits about 5 seconds).
  If that button was already used by another action, the two are swapped. Also Stick Deadzone and Reset to Defaults.

### Where things are saved

Everything is stored on the Memory Stick in `PSP\SAVEDATA\SM64PORT\`:

| File | Contents |
|---|---|
| `sm64_save_file.bin` | Your game progress (stars, coins…) |
| `sm64config.txt` | All your settings (graphics, audio, controls) as plain text |
| `freeze.txt` | Only after a freeze: a small report of what the game was doing (see Troubleshooting) |

`sm64config.txt` can be opened with Notepad. Each line is `name = value`. To start from scratch, delete the file (or use *Reset to Defaults*).

## 5. Troubleshooting

**`docker` is not recognized / "The term 'docker' is not recognized"**
Docker Desktop is not installed, or PowerShell was open before installing it. Install it, **close PowerShell and open a new one**.

**"error during connect…" / "Cannot connect to the Docker daemon" / "docker daemon is not running"**
Open **Docker Desktop** and wait for **"Engine running"**, then try again.

**Docker Desktop says WSL 2 or virtualization is not available**
- Run `wsl --install` in an administrator PowerShell and restart.
- Enable virtualization in the BIOS/UEFI (Intel VT-x / AMD SVM).

**"running scripts is disabled on this system"**
Start the script exactly like this: `powershell -ExecutionPolicy Bypass -File .\build_psp.ps1`.

**`Failed to open baserom.us.z64!`** (or `baserom.jp/eu/sh.z64`)
The ROM is not in the right place or has the wrong name. It must sit **next to `Makefile`** and be called exactly `baserom.<version>.z64`
(with extensions visible, check it is not `baserom.us.z64.z64`). For Shindou you need `baserom.sh.z64` **and** `baserom.jp.z64`.

**`baserom.us.z64 has the wrong hash!`** (or the same with `jp`, `eu` or `sh`)
It is not the ROM of that version, or it is in another format. Redo [Step 1](#step-1--check-your-rom).

**The build stops with an error halfway, or you changed something and it behaves strangely**
Run it again with `-Clean`: `powershell -ExecutionPolicy Bypass -File .\build_psp.ps1 -Clean`.

**"No space left on device"**
Free some disk space (Docker needs a few GB). In Docker Desktop you can also run *Troubleshoot → Clean / Purge data*.

**The build is very slow**
The first one always is (see Step 5). Keep the project on a normal drive (not a network drive) and close heavy programs.
In Docker Desktop → Settings → Resources you can give it more CPUs.

**The game does not appear in the XMB**
Check the paths are exactly `PSP\GAME\SM64\EBOOT.PBP` and `PSP\GAME\SM64\SM64.PRX` (both files, same folder) and that your PSP has custom firmware. If you see a "Loading the game…" screen with an error, `SM64.PRX` is missing or in another folder. Re-copy the file if it is corrupt.

**The screen stays black after turning on TV Output**
Start the game again: if TV was turned on and did not last about 5 seconds, the game switches TV Output back to *Off* by itself on the next launch and uses the PSP's own screen.

**The game freezes**
If the game stops drawing frames for about 4 seconds, a small watchdog writes `freeze.txt` in `PSP\SAVEDATA\SM64PORT\` (and rewrites it every 4 s while the freeze lasts, up to 12 s). It lists where the main thread was, what each thread is waiting on, the GPU and audio-processor state, the level / Mario action and the battery level and voltage. If the game recovers by itself it adds a line saying so. Attach the file to your issue. If the whole console locks up so hard that no code runs, no file can be written: in that case the *absence* of `freeze.txt` is itself useful information.

**Anything else**
Open an *Issue* on the repository's GitHub page and include the last 20–30 lines of the build output.

## 6. Building on Linux / WSL

You can use the same Docker image, from a Linux terminal (or inside WSL with Docker running), at the project root with your ROM (`baserom.us.z64`, for example) in place. Replace `VERSION=us` with `jp`, `eu` or `sh` for the other versions:

```bash
docker build -t sm64psp - < Dockerfile.psp
docker run --rm -v "$PWD:/sm64" -w /sm64 sm64psp make TARGET_PSP=1 pbp VERSION=us -j$(nproc)
```

The result is again `build/<version>_psp/mario64/` (`build/us_psp/mario64/` for US), with `EBOOT.PBP` + `SM64.PRX`. (On Linux, files created by Docker belong to `root`; fix it with `sudo chown -R $USER .` if you need to.)

**Without Docker**: install the [PSP toolchain (pspdev)](https://github.com/pspdev/pspdev), plus `python3` and `build-essential`/`audiofile` development packages, then:

```bash
make TARGET_PSP=1 VERSION=us -j4        # builds the ELF/PRX
make TARGET_PSP=1 VERSION=us pbp        # builds build/us_psp/mario64/{EBOOT.PBP,SM64.PRX}
```

Audio is generated through the Media Engine with `libme-core`; no external sound PRX is needed next to the EBOOT.

## 7. For developers

### Profiling with gprof

1. Build with profiling: `make TARGET_PSP=1 PROFILE_PSP=1` (add `pbp` for an EBOOT).
2. Run it on the PSP or emulator. `gmon.out` is written when the game exits normally.
3. Copy `gmon.out` back and analyse it: `gprof build/us_psp/sm64.us gmon.out > profile_report.txt`

Profiling adds overhead. With it enabled, the PBP uses the ELF directly instead of a PRX.

### Building a release package

The packages of the "install from a release" section are made with `make TARGET_PSP=1 release VERSION=us -j8` (or `.\build_psp.ps1 -Version us -Release`); the installer is in `psp/installer/`. See `tools/psp/README.md`.

### Other targets (unchanged from upstream, not maintained here)

The upstream project can also build native **Linux** and **Windows (MSYS2)** executables and N64 ROMs.
See [sm64-port/sm64-port](https://github.com/sm64-port/sm64-port) and [n64decomp/sm64](https://github.com/n64decomp/sm64) for those instructions.

### Project structure

```
sm64
├── actors: object behaviors, geo layout, and display lists
├── asm: handwritten assembly code, rom header
├── assets: animation and demo data
├── bin: C files for ordering display lists and textures
├── build: output directory
├── data: behavior scripts, misc. data
├── enhancements: example source modifications
├── include: header files
├── levels: level scripts, geo layout, and display lists
├── lib: SDK library code
├── psp: PSP icon, background and sound for the EBOOT, PSP-specific textures, `dvemgr` (the TV-output helper module)
├── rsp: audio and Fast3D RSP assembly code
├── sound: sequences, sound samples, and sound banks
├── src: C source code for game
│   ├── audio: audio code
│   ├── buffers: stacks, heaps, and task buffers
│   ├── engine: script processing engines and utils
│   ├── game: behaviors and rest of game source (psp_options.c = the Options menu)
│   ├── goddard: Mario intro screen
│   ├── menu: title screen and file, act, and debug level selection menus
│   └── pc: port code, audio and video renderer (PSP: gfx_psp.c, audio_psp.c, psp_me.c)
├── text: dialog, level names, act names
├── textures: skybox and generic texture data
└── tools: build tools
```
